# ADR 0003 — Internationalization: lightweight custom i18n

- **Status:** accepted
- **Date:** 2026-11-10
- **Context:** CodeWash feature mission "Translation".

## Context

The game ships with English strings hardcoded across components. The mission asks
for a way to **change the display language**, a language **list/button** in the
menu, and a second language — while **not hardcoding anything**, so that adding
further languages later is trivial. The project is a legacy React/Vite/Electron
app we must not rewrite.

## Decision

Build a **small, dependency-free i18n layer**:

- **Pure core** (`src/i18n/translate.js`): dotted-key lookup, `{placeholder}`
  interpolation, and fallback (active language → English → the key itself). No
  React, no I/O → 100% unit-testable.
- **Config** (`src/i18n/config.js`): the single registry of languages, plus
  `localStorage` persistence of the chosen language. Nothing about languages is
  hardcoded elsewhere.
- **Locales** as plain JSON (`src/i18n/locales/en.json`, `fr.json`). French is
  the second language.
- **Thin React binding** (`src/i18n/I18nContext.jsx`): holds the active-language
  state and exposes `t(key, vars)` via `useI18n()`. A `LanguageSelector`
  component renders one button per registered language.

Adding a language = add a JSON file + one line in `translations.js` + one entry
in `config.js`. No other change. Documented in `docs/FEATURES.md`.

## Consequences

- No new runtime dependency; the core is fully tested (100% lines).
- Translation is **incremental**: the Settings drawer, Bug Report modal and the
  language selector are translated now; the remaining in-game strings (mostly in
  the big `App.jsx` / `SkillCard.jsx` god components) are migrated key-by-key as
  those files are refactored. Tracked as **DEBT-12** so the residual is explicit.
- A missing key degrades gracefully (English, then the key) instead of crashing.

## Alternatives considered

- **`react-i18next` / `i18next`:** powerful but a heavy dependency for a kids'
  game, and the pluralization/namespace machinery is overkill here. Our needs
  (lookup + interpolation + fallback) are a few tested functions. Rejected, but
  the `t()` surface is compatible enough to migrate later if ever needed.
- **Hardcoded per-language components:** violates the "no hardcoding" rule and
  does not scale. Rejected.
